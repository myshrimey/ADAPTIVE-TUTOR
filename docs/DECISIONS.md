### v34 (2026-10-15): founder's answers to the two master-prompt decisions, and how they were implemented
**Decision 1 — pricing/positioning (founder, 2026-10-15): switch to ₹999 "Sahayak Complete Board Preparation" (CBSE Class 10, 2027).** Implemented as one config object (`BOARD_PREP_OFFER`: ₹999, 240 days) so price/duration change in one place. The 240-day length is MY assumption (covers an October-2026 start through the 2027 board window) — **the founder has not chosen the duration; confirm or change it.** ₹999 remains a price *hypothesis*, stated as such on the offer page. Table/route names still say "pilot" on purpose (renaming live tables is risk with no user benefit). Terms/limitations/payment copy updated but remain founder-review drafts; refund terms are still unwritten (draft says "handled individually").
**Decision 2 — add the other 4 subjects now (founder): Social Science, English Language & Literature, Hindi Course A, Computer Applications.** Implemented honestly as **Pilot**, not Ready: the master prompt itself forbids claiming a subject is supported before it passes the quality gates and says AI output must not be treated as verified. So the three new subjects ship with AI-written starter content marked `needs_review`, visibly labelled "Pilot" in onboarding, diagnostic picker, dashboard, report and offer page. Promotion to Ready needs a human review (see `docs/CONTENT_STATUS.md`).
**Multi-subject needed no new table:** `learning_goals` already had one row per (student, subject); onboarding just only ever created one. Added `learning_goals.activated_at` to say which subject is active (learner model now orders by it).
**Content verification status is information, with one hard rule:** `rejected` questions are never served; `needs_review` questions are still served (otherwise the new subjects would have nothing to ask). Maths/Science existing banks default to `verified` meaning "curated and in real use", NOT teacher-certified — stated in CONTENT_STATUS.md.
**Check-ins: context shapes the session, never the grade.** Mood/focus/confidence live in `session_checkins`, never in `mastery_states`. "Recovery mode" (≥2 of: tired/stressed/not-great mood, very distracted, confidence ≤3) only eases the first 3 questions of that one session. Everything is optional/skippable so it can't become a wall. Parent-facing wording is neutral; the confidence-vs-performance note appears only after ≥3 sessions with ≥3 unaided attempts each and a clear pattern.
**Confidence is shown as a trend** (latest, previous, 7-day, 30-day, direction, per-subject, before→after), never as "High/Moderate". Confidence and mastery are shown separately.
**"Evidence" in the parent report describes the data, not the child:** insufficient (<3 skills assessed or <20% coverage), limited (<60%), good (≥60%). "Insufficient evidence" is a legitimate outcome and is displayed plainly.
**NOT built, by decision:** Maths Basic/Standard split (would re-key live mastery data — own round); 7-stage assessment ladder, timed/mock exams, board-readiness bands beyond coverage+evidence; hard paywall (today payments are tracked and displayed but nothing blocks a signed-in student — **founder decision needed on whether/when to enforce access**); animations (still needs a named moment).
**Bug found:** parent report's mastery query used a non-existent `skills → chapters` relation (v29), so current mastery never loaded; fixed in v34.

### RLS fix for explanation caching (2026-10-12)
**Decision:** Add an explicit `for update ... using (true) with check (true)` policy, scoped to `authenticated` only, on `diagnostic_questions` and `questions`.
**Alternative considered:** Switch the write-through cache to use the service-role client instead of the session client.
**Why this way:** The explanation text is shared, non-private content (every student reads the same question bank) — it already has an open-to-all-authenticated SELECT policy, so an equally open UPDATE policy doesn't create a new privacy or security exposure, and it's a one-line, fully reversible change. Switching to a service-role client would also work but is a larger code change (new client wiring inside `packages/core`) for no extra safety benefit here.

### Payment: offline UPI/QR only, no embedded QR code (2026-10-12)
**Decision:** The app shows the pilot offer, price, and a "contact the founder for payment details" step; it does not display or generate any UPI ID or QR code itself.
**Why:** The founder stated he will share the UPI ID/QR directly with each parent himself. This also avoids ever needing to put real payment details into a file that gets committed to git or deployed to a public URL, which is safer by default.
**NEEDS FOUNDER APPROVAL:** none at this layer (no payment details are embedded) — but the admin "mark as confirmed" workflow and its exact wording should be reviewed once built.

### Payment confirmation: manual admin workflow, reusing `/admin/feedback`'s pattern (2026-10-12)
**Decision:** A new `/admin/payments` page, gated the same way `/admin/feedback` already is (an `ADMIN_EMAILS` environment variable, compared against the signed-in user's email) — not a new, separate auth system.
**Alternative considered:** A fully separate admin-role table/column.
**Why:** Smallest safe change; the existing pattern is already live and understood. A payment can only ever be marked "confirmed" by a signed-in user whose email is in `ADMIN_EMAILS` — an ordinary student/parent account can never do this, enforced both in the UI and by an RLS policy on the payments table itself (defense in depth).

### Language: dictionary + toggle, not routed locale paths (2026-10-12)
**Decision:** A single `packages/core/i18n/` dictionary (English + Hindi key-value pairs) plus a lightweight `LanguageProvider`/cookie, rather than Next.js's built-in i18n routing (`/en/...`, `/hi/...`).
**Why:** Routed locales would touch nearly every route and link in the app — a much larger change than the brief's "use the existing architecture and lightweight translation resources" asks for. A dictionary + cookie covers every required surface (nav, dashboard, diagnostic, messages, legal pages, footer) without restructuring routes.
**Explicit non-goal (per brief):** the question bank itself is not translated. Any question shown is labeled as English-only.

### Question-bank scale ("~1000 per skill") — RESOLVED, architecture changed instead of just content volume (2026-10-14)
**Founder's answer (2026-10-14):** wants the deeper per-subject push, confirmed as "~1000 questions per skill," AND asked whether the tool can generate questions/answers/quizzes/solutions itself based on skill + difficulty, without relying on a pre-authored bank — and if so, to build that.
**Decision:** Yes, and this is the real answer to the scale question, not a separate feature. Rather than hand-authoring tens of thousands of static rows (which v31's note flagged as infeasible to verify at that scale, and which earlier rounds showed hits real per-skill content ceilings), v32 generalizes and extends the AI question generator that already existed for learning-session practice (`question-engine/selector.ts`, pre-dating this round) to also cover the post-session quiz. Every quiz for a skill whose bank is thinner than 5 questions now has AI-generated questions — each with a worked solution, generated in the same call as the question itself — filling the gap, and **every generated question is saved back into the bank** (`source: 'generated'`) rather than thrown away after one use. So instead of a single enormous authoring effort that produces a fixed number, the bank for a skill grows a little every time a student is served a question that skill's bank didn't already have — asymptotically approaching (and for some skills exceeding) 1000, with no hard ceiling imposed by this system, while naturally topping out lower on skills that genuinely don't support that many distinct questions.
**What this round fixed along the way:** the existing generator had a real bug — its prompt was hardcoded to "CBSE Class 10 Maths," so a Science skill falling back to AI generation would have silently gotten a Maths-flavored question. Now subject-aware (reads the skill's real subject off the curriculum, Mathematics or Science). It also only generated the question+answer, leaving the explanation for a separate, lazy, on-a-miss AI call; it now asks for the worked solution in the same call, which is both cheaper (no second call later) and more accurate (asking the model to show its own working alongside the final answer catches more of its own arithmetic slips than asking for a bare value).
**What's deliberately unchanged:** the diagnostic test itself still draws only from the curated static bank, not AI generation. A new student's very first diagnostic is the one place in this app where a fixed, known-correct, consistently-scored set of anchor questions is more valuable than variety — this is also almost certainly where the 25-60-per-skill count from earlier rounds is actually fine, since no one student sees more than a handful of questions per skill in one diagnostic anyway. Generation happens where repeated practice volume actually matters: learning-session practice questions and the post-session quiz.
**Safety net kept in place:** every generated question is schema/shape-validated before being shown or saved (non-empty prompt, a real question type, MCQ options present when required, a non-empty expected answer and explanation) — a malformed response is discarded rather than served or persisted, and generation failures (AI down, bad JSON) degrade to "serve what the bank already has" rather than breaking the quiz or session.

### Follow-up (v33, 2026-10-14): diagnostic test also gets the generation safety net, but stays bank-first
**Decision:** `startDiagnostic`'s anchor-skill plan and `answerDiagnosticQuestion`'s prerequisite-check insertion now both fall back to AI generation (via `pickOrGenerateQuestionForSkill`) when the bank has literally no question for that test+skill — same validated-and-persisted pattern as the quiz. This does NOT change the earlier decision that the diagnostic prefers its curated bank: `pickQuestionForSkill` (the existing bank lookup) is tried first every time, and generation only runs on an actual empty result. In the current data this safety net is expected to rarely or never fire (every anchor/prerequisite skill already has at least one authored question) — it exists so a newly added chapter/skill doesn't silently block a student's diagnostic, not as a way to introduce variety into the diagnostic's otherwise-fixed anchor set.
**Also done (v33):** figures now render during the regular learning-session chat (not just diagnostic/quiz) — `questions.figure_url`/`figure_caption` (added in migration 0010 but only read by the quiz/diagnostic until now) are now selected by `question-engine/selector.ts` and threaded through the orchestrator's `activeQuestion` into `/learn`'s answer UI.

### Score visuals: reuse `MasteryArc`, not a new gauge component (2026-10-14)
**Decision:** The diagnostic results screen, the post-session quiz banner, and `/report` now use the same `MasteryArc` SVG arc component already live on `/progress` and `/parent/[token]`, rather than introducing a second gauge style.
**Why:** Consistency (a parent/student seeing a score arc on one page should see the same visual language elsewhere), and it's a working, already-tested component — no reason to add a second one.

### Question figures: reuse existing learning-diagram SVGs where possible, generic per-skill not per-question (2026-10-14)
**Decision:** Figures are attached per-skill (one shared, non-specific image for every question on that skill), reusing the already-drawn `learning-diagrams` SVGs for 12 skills, plus one new frequency-distribution-table SVG for 2 statistics skills — not a bespoke image authored per individual question.
**Alternative considered:** A unique figure per question, matching that question's exact numbers.
**Why this way:** Matches the pattern already established for teaching diagrams (`packages/core/learning-diagrams/mapping.ts`) — the image illustrates the setup/shape/circuit, and the question's own prompt text carries the specific numbers for that question. Authoring a unique, numerically-accurate figure per question would be a much larger effort (and a correctness risk — a mismatched number in a figure is worse than no figure) for a 10-day MVP; this gets the genuine comprehension benefit (seeing the shape/circuit/table layout) without that risk. Only 14 skills got a figure this round, deliberately curated to where a question is meaningfully harder without one — not every skill that already has a learning-diagram.

### Diagnostic-save symptom — RESOLVED (2026-10-13)
Root cause found by reading real production data (not speculative): the save path itself always worked; students were re-opening an unfinished diagnostic and getting a brand-new attempt each time, orphaning the old one. Fixed in v30 (resume-in-progress logic), confirmed working live by the founder. See `docs/BUILD_LOG.md`'s 2026-10-13 entries for the full root-cause trail.
